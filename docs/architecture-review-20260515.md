# Resilix Architecture & Scalability Review (2026-05-15)

## 1) Current architecture and execution flow

### Repository-level architecture
Current implementation is a **static demo artifact stack** (GitHub Pages style), not a modular runtime platform:

- **Presentation layer**: static HTML demos with embedded JS logic (`index.html`, `docs/index.html`, `public/aitas-demo.html`).
- **Minimal logic module**: one utility-like explainability function (`src/explainability.js`).
- **Data contract layer**: a JSON schema for output shape (`data/schema.json`).
- **Output artifacts**: precomputed sample inferences (`output/*.json`) and narrative review markdown (`output/reviews/*.md`).
- **Source corpus**: raw source files for one account (`data/sources/aitas/*`).

### Runtime execution flow (today)
1. User opens static page.
2. Inline JS in HTML performs local calculations / text substitution.
3. UI renders fixed or form-derived metrics and narrative cards.
4. No explicit pipeline executes from raw signals → mapped features → scored risks in code.
5. JSON outputs in `output/` are effectively offline snapshots, not generated by a traceable runtime orchestration layer.

### Effective dataflow (inferred)
There is an **implicit** pipeline expressed in README and outputs:

`public ESG/job signals` → `vMEME mapping` → `contradiction/dependency inference` → `risk scenario + recommendations`

But this is represented as documentation/content, not as isolated code modules with deterministic interfaces.

## 2) Most fragile system design element

### Primary fragility: epistemic + computational coupling in presentation artifacts
The most fragile part is the coupling of:
- interpretive ontology claims (Spiral Dynamics/vMEME labels),
- quantified risk outputs (e.g., 72%), and
- UI/demo-layer hardcoding,

without a separable, auditable inference layer.

Consequences:
- You cannot prove how a score was computed from raw evidence.
- Confidence is simplistic (`signals.length` heuristic), which can diverge from enterprise evidence standards.
- Any vertical-specific extension requires editing mixed HTML/JS copy and static outputs, increasing drift and inconsistency risk.

## 3) Scalability evaluation

### A) Multiple verticals
**Current readiness: low-to-medium (concept-level yes, implementation-level no).**

Why constrained:
- No config package per vertical (taxonomy, signal extractors, weights, contradiction rules).
- No versioned mapping registries.
- No isolated domain adapters.

Result: each new vertical likely becomes a copy-modify demo branch.

### B) Enterprise clients
**Current readiness: low.**

Enterprise constraints unmet:
- No ingestion connector abstraction (APIs, batch files, HRIS/ERP/ATS adapters).
- No data lineage/provenance graph beyond source list strings.
- No policy/audit boundaries between observed facts and inferred hypotheses.
- No model governance/versioning evidence for “why this changed between runs”.

### C) Configurable inference layers
**Current readiness: low.**

Needed but absent:
- stage-separated inference contracts (`observed`, `derived`, `hypothesis`).
- rule engine or declarative config for mapping/scoring.
- plug-in mechanism for optional interpretive overlays.

Today’s architecture hardcodes these concerns into static output narratives and inline scripts.

## 4) Improvement directions (targeted)

### Modularity
- Introduce explicit pipeline packages:
  - `ingestion/`
  - `normalization/`
  - `mapping/`
  - `scoring/`
  - `explainability/`
  - `rendering/`
- Define stable interfaces with JSON schemas between stages.
- Keep interpretive frameworks (e.g., Spiral Dynamics) as optional adapters, not core dependency.

### Explainability
- Emit per-score evidence objects:
  - `metric_id`, `value`, `direction`, `weight`, `source_ref`, `transform_ref`, `confidence`, `assumption_tags`.
- Add contradiction trace records (which signals conflict, conflict rule id, severity).
- Separate factual evidence from interpretive overlay in output payload.

### Maintainability
- Replace inline JS monoliths in HTML with imported modules.
- Move scenario constants and translations into versioned config files.
- Add golden test fixtures for each stage (`signal -> mapped features -> score -> explanation`).

### Offline-first operation
- Keep local-first execution path for scoring in-browser/edge worker for demos.
- Store packaged rule/config bundles locally and signed (versioned manifests).
- Queue source ingestion updates and re-run scoring when connectivity returns.

## 5) Focused risk analysis by subsystem

### Signal ingestion
Current state: implied only; sources are files and manual artifacts.

Risks:
- No source connector abstraction.
- No normalization contract for heterogeneous evidence types.
- Missing provenance granularity (source paragraph/section offsets).

Recommendation:
- Create `signal_record` canonical schema with strict required metadata:
  `source_id`, `source_type`, `captured_at`, `extractor_version`, `verbatim_excerpt`, `confidence`.

### Mapping pipeline
Current state: conceptual vMEME mapping; no dedicated mapper module in repo.

Risks:
- Ontology lock-in prevents cross-framework operation.
- Non-deterministic human interpretation likely hidden in content generation.

Recommendation:
- Split into two maps:
  1) **defensible feature map** (e.g., hierarchy emphasis, autonomy signal, centralization score),
  2) **optional ontology map** (Spiral overlay) behind feature flags.

### Scoring architecture
Current state: score outputs exist, but computational path is opaque.

Risks:
- Perceived pseudo-precision (exact percentages without model card/governance).
- Hard to calibrate with internal enterprise data.

Recommendation:
- Use composable score graph:
  - `dependency_score`
  - `contradiction_score`
  - `execution_gap_score`
- Each node exposes formula metadata, dependencies, and uncertainty bounds.

### Config-driven extensibility
Current state: limited schema and static payload examples.

Risks:
- Extension by copy-paste.
- Rule drift across demos/clients.

Recommendation:
- Add registry-driven configs:
  - `verticals/<id>/signals.yml`
  - `verticals/<id>/mapping.yml`
  - `verticals/<id>/scoring.yml`
  - `verticals/<id>/narrative_templates.yml`
- Include semantic versioning + compatibility checks with pipeline engine.

## Practical target architecture (concise)

1. **Signal Layer (facts only)**
2. **Feature Layer (defensible abstractions)**
3. **Risk Scoring Layer (calibrated, uncertainty-aware)**
4. **Interpretive Overlay Layer (optional frameworks)**
5. **Narrative/UX Layer (progressive disclosure + evidence drilldown)**

This preserves your current strategic differentiator (contradiction and dependency intelligence) while reducing epistemic fragility and improving enterprise scalability.
